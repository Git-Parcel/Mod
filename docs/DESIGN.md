# Git Parcel 设计文档

## 文档定位

本文描述 Git Parcel 当前实现所遵循的系统设计，并为后续功能演进规定边界。文档以代码现状为准，不以 README 或早期设想为准。

Git Parcel 是一个服务端必需的 Minecraft 模组。它将世界中的长方体区域抽象为“地块”（Parcel），使用可扩展格式保存其方块和实体数据，并借助 Git 提供版本历史、恢复以及跨服务器共享能力。

当前阶段优先保证核心功能、数据安全和服务端一致性。现有调试界面不属于产品界面，也不作为近期改进目标。未来用户界面计划使用 Modern UI，但界面只能作为服务端能力的客户端入口，不能成为业务状态的权威来源。

## 设计目标

- 以服务端为唯一权威，确保多人环境中的权限、数据和世界状态一致。
- 将地块内容保存为可读、可迁移、可进行版本管理的目录快照。
- 将“保存当前快照”和“创建 Git 版本”拆分，避免隐式产生提交。
- 同时支持世界内部版本库和服务器管理的共享版本库。
- 在不切换 Git 工作树或破坏当前状态的前提下查看、恢复历史版本。
- 对路径、远程地址、凭据和并发操作设置明确的安全边界。
- 隔离 Minecraft、加载器、存储格式和 Git 实现，便于多版本维护与后续替换。
- 为未来 Modern UI 提供稳定的服务端模型和同步接口。

## 非目标

当前设计不试图解决以下问题：

- 改进或产品化现有调试界面。
- 由客户端直接读写版本库、磁盘文件或权威地块状态。
- 自动合并有冲突的 Git 历史。
- 在拉取远程版本后自动修改正在运行的世界。
- 提供完整的 Git 托管、代码审查或通用仓库管理功能。
- 在核心工作流尚未稳定前确定最终 Modern UI 交互设计。

## 总体架构

系统按职责分为以下层次：

```text
命令 / 未来 Modern UI
          |
          v
服务端用例层：ParcelService、共享仓库服务、异步 Git 操作
          |
     +----+--------------------+
     |                         |
     v                         v
领域与权限模型            存储格式与 Git 服务
     |                         |
     +------------+------------+
                  v
          Minecraft 世界与文件系统

服务端权威状态 --同步消息--> 客户端只读镜像 --渲染/界面--> 用户
```

主要代码区域的职责如下：

- `common/api`：地块、格式、内容、权限等稳定领域类型。
- `common/impl`：不依赖具体加载器的算法和实现。
- `common/minecraft/logic`：服务端世界协调、持久化、网络消息和 Minecraft 公共逻辑。
- `common/platform`：Fabric 与 NeoForge 的平台适配。
- `server/minecraft/logic`：命令、共享/系统存储和异步 Git 操作。
- `client`：服务端状态的客户端镜像、渲染和当前调试界面。

依赖方向应从外层适配代码指向公共领域和服务。公共领域模型不应反向依赖具体加载器，客户端也不应承载只有服务端才能验证的业务规则。

## 服务端权威边界

服务端负责：

- 地块注册表及其增删改。
- 地块和世界级权限判断。
- 世界内容的读取与写入。
- 格式能力的实际可用性。
- 文件系统布局、Git 历史和远程同步。
- 共享仓库目录及其元数据。

客户端只维护服务端下发的地块和格式能力镜像，用于渲染与交互展示。客户端提出操作意图后，服务端必须重新解析目标、校验权限和前置条件，不能信任客户端提供的结果。

该边界也是未来 Modern UI 的基础：UI 可以提供筛选、预览、进度和确认交互，但最终操作仍通过服务端用例执行。

## 领域模型

### 地块

`Parcel` 是核心聚合，使用 UUID 作为稳定标识，包含：

- `ParcelMeta`：格式规格、数据版本、尺寸、锚点、名称、描述、作者、标签、模组依赖及实体排除设置。
- `ParcelTransform`：镜像、旋转、平移和枢轴等放置变换。
- `Visual`：客户端渲染所需的视觉配置。
- `PermissionConfig<ParcelPermissions>`：该地块的权限配置。
- 格式配置：由具体格式解释的 JSON 数据。
- `ParcelLocation`：地块内容所在版本库及相对路径；为空时表示世界内部版本库。

元数据描述内容本身和导入约束，变换描述内容如何映射到当前世界。二者分离后，同一份内容可以在不同位置和朝向使用，而不需要改写内容文件。

### 地块位置

地块位置支持三种状态：

- 无位置：使用世界内部、按地块 UUID 隔离的版本库。
- 直接位置：记录版本库目录和仓库内相对路径，主要用于兼容已有数据。
- 共享位置：记录共享仓库的符号名称和仓库内相对路径。

新建共享绑定优先使用符号名称，不把服务器绝对路径写入地块数据。这样可以移动服务器目录、切换游戏存储与系统存储，而不必批量修改地块。

一个位置只能引用直接版本库或共享仓库之一。相对路径必须是非空、安全的仓库内路径，不能是绝对路径、不能逃逸仓库根目录，也不能包含 `.git`。共享地块路径还不能与仓库根部的 `meta.json` 冲突。

### 权限

权限分为世界级和地块级：

- 世界级权限控制格式列表、地块列表、创建、删除、配置地块，以及查看和管理共享仓库。
- 地块级权限控制保存、加载、配置和提交。

权限等级映射到 Minecraft 原版权限体系，包括所有人、管理员级别以及所有者。创建地块时复制世界默认地块权限，随后每个地块独立修改，避免默认配置的后续变化意外影响已有地块。

涉及多个地块的操作应先完成全部目标的权限和前置条件检查，再开始修改，尽量避免只完成一部分目标。

## 地块生命周期

典型生命周期如下：

```text
选择世界区域
    -> 创建地块元数据
    -> 保存内容快照
    -> 按需创建提交
    -> 查看历史 / 恢复历史
    -> 发布到共享仓库或绑定已有共享内容
```

创建地块时，服务端检查尺寸、最大体积、与已有地块的空间关系、格式可用性和权限。注册完成后，地块进入当前维度的权威集合，并同步给相关客户端。

删除地块首先是从服务端注册表中删除该逻辑对象。仓库数据的删除具有更高破坏性，不能仅因删除逻辑地块而被隐式扩大；共享仓库更不能由单个地块操作顺带删除。

## 持久化设计

### Minecraft SavedData

每个维度使用 `GitParcelLevelSavedData` 保存该维度的地块集合。世界级的权限、默认地块权限和最大地块体积由 `GitParcelWorldSavedData` 保存。

维度数据和世界数据分离，原因是地块具有明确的维度归属，而权限策略和全局限制应在整个服务器世界中一致。

### 世界内部仓库

未绑定共享位置的地块使用独立 Git 仓库：

```text
<world>/gitparcel/parcels/<parcel-uuid>/
├── .git/
└── parcel/
    ├── parcel.json
    ├── config.json
    └── data/
```

每个地块使用独立仓库，能够降低互相干扰和误提交其他地块的风险，也使本地历史操作天然限定在单个地块内。

### 共享仓库

共享根目录由配置选择游戏目录或 SystemStorageLib 提供的系统数据目录，也可由 `GITPARCEL_SHARE_DIR` 环境变量覆盖。其逻辑结构为：

```text
<shared-root>/
├── repos.json
└── <repository-name>/
    ├── .git/
    ├── meta.json
    └── <parcel-relative-path>/
        ├── parcel.json
        ├── config.json
        └── data/
```

`repos.json` 是服务器管理的仓库目录，位于所有 Git 仓库之外。仓库内的 `meta.json` 记录该仓库公开管理的地块路径。磁盘上存在某个目录不等于它自动成为可导入地块；共享元数据是显式边界。

### 快照替换

保存不是在现有地块目录内逐个覆盖文件，而是先在同级临时目录生成完整快照，再替换目标目录。替换时保留备份；如果安装新快照失败，则恢复旧目录。

这一策略保证：

- 已删除的方块、实体或格式文件不会残留在新快照中。
- 读取者不会看到写到一半的混合状态。
- 常见安装失败能够回退到原快照。

调用者没有显式给出新格式配置时，应保留已有配置。是否忽略实体同时受命令参数和地块元数据约束，任一方要求排除实体时都不能写入实体。

## 格式系统

格式由 `ParcelFormat.Spec` 标识，其中包含格式 ID 和版本。`ParcelFormatRegistry` 根据规格查找对应的读写器。当前内置实现包括 MVP、Parcella 和 Structure Template 等格式。

格式读写器不直接拥有世界生命周期，而是通过内容源和内容汇抽象访问方块、方块实体与普通实体：

```text
Minecraft 世界 -> ParcelContentSource -> 格式写入器 -> data/
Minecraft 世界 <- ParcelContentSink   <- 格式读取器 <- data/
```

这种设计将“从世界取得什么”和“如何编码”分开，使格式可以独立演进。格式专属参数由 `ParcelFormatConfig` 表达并存入 `config.json`。`ParcelMeta.dataVersion` 用于在读取旧 Minecraft 数据时执行必要的数据迁移。

导入或恢复到世界时，方块更新采用面向批量结构写入的更新标志，向客户端同步最终状态，同时避免逐方块触发不必要的副作用。恢复已有地块的历史版本前必须校验尺寸和锚点兼容性，防止历史内容越出当前地块边界。

## Git 工作流

### 保存与提交

`save` 只将当前世界内容写成工作树快照；`commit` 才创建 Git 版本。两步分离便于用户检查、批量保存或决定提交说明，也避免每次写盘都污染历史。

没有实际变化时不创建空提交。提交作者来自命令执行者；玩家使用基于 UUID 的稳定身份，控制台等服务端来源使用本地服务端身份。

在共享仓库中，提交必须限定到目标地块路径。发布地块时，地块快照和仓库根部 `meta.json` 的登记需要进入同一个提交，从而避免历史中出现“内容存在但未登记”或“已经登记但内容不存在”的中间版本。

### 历史与恢复

历史查询按地块路径过滤，并按从新到旧的顺序返回。恢复历史版本不会执行 Git checkout，也不会移动 HEAD、修改暂存区或整体替换工作树。

实现会直接遍历目标提交树，把指定地块子树导出到临时目录，然后按普通地块加载流程校验并写入世界。只接受普通文件和可执行文件，拒绝符号链接及其他特殊条目；所有导出路径都必须再次验证不能逃逸临时目录。操作结束后清理临时文件。

因此，“恢复”表示将某个历史快照应用到当前世界，不表示把仓库永久切换到历史分支。用户如需把恢复后的世界状态写回当前历史，应再次执行保存和提交。

### 共享仓库工作流

共享仓库提供以下核心操作：

- 创建本地共享仓库或从受管 HTTPS 地址克隆。
- 列出共享仓库及仓库中登记的地块。
- 将世界内部地块发布到共享仓库。
- 将现有地块绑定到共享仓库中的兼容路径。
- 解除绑定，使后续保存重新使用世界内部仓库。
- 从共享仓库工作树导入新地块。
- 异步执行 fetch、pull 和 push。

发布仅适用于尚未绑定共享位置的世界内部地块，且目标路径必须尚未被占用。绑定会校验登记状态、元数据文件、尺寸和锚点，但不会自动把共享内容加载进世界。解除绑定也不会删除原共享内容。

导入从共享仓库当前工作树创建新的地块 UUID，使用世界默认权限的副本，并在通过体积、相交和格式校验后写入世界、注册及同步。

pull 只更新仓库文件，不自动修改实时世界。远程内容进入世界必须通过显式导入或历史恢复流程完成。这是防止一次网络同步绕过 Minecraft 权限、空间校验和用户确认的关键边界。

## 远程同步与任务模型

clone、fetch、pull 和 push 可能受网络延迟影响，因此由 `GitOperationManager` 在服务端后台执行。管理器使用有界工作线程和有界队列，记录任务 ID、所有者、仓库、状态及结果摘要。任务状态包括排队、运行、成功、失败和取消，并保留有限数量的近期记录供命令或未来 UI 查询。

服务器停止时取消尚未完成的任务。异步任务不得直接在后台线程修改 Minecraft 世界、命令源或客户端连接；涉及游戏状态的后续处理必须回到合适的服务端执行上下文。

同一规范化仓库路径的 Git 操作串行执行。共享仓库还使用仓库级锁，协调地块保存、提交、历史读取、恢复、发布、导入和远程同步，防止工作树与索引被并发操作破坏。不同仓库可以并行工作。

pull 要求工作树干净，并且只允许快进更新。push 要求工作树干净、当前分支明确且已配置上游。发生分叉、冲突或缺少远程配置时显式失败，不尝试自动合并或猜测目标分支。

## 网络同步

服务端在玩家加入时同步：

- 服务端实际支持的格式及能力。
- 玩家所在维度的完整地块集合。

玩家切换维度时重新进行完整地块同步。运行期间的创建、更新和删除使用增量地块消息。完整同步会替换客户端镜像，增量同步只覆盖变更项并移除指定 UUID。客户端断开连接时清空镜像，防止旧服务器状态泄漏到下一次连接。

目前同步的是服务端领域状态，而不是磁盘仓库的任意文件。未来 UI 所需的新信息应优先设计为最小、明确、可鉴权的查询或事件消息，避免把仓库文件系统直接暴露给客户端。

客户端可以按需请求共享仓库和异步 Git 任务状态。服务端对客户端查询进行频率限制，分别使用“查看共享仓库”和“管理共享仓库”权限鉴权，并返回公共只读快照，而不是服务端实现对象。仓库快照包含类型、无凭据远程地址、最近同步时间和已登记地块路径；任务快照包含生命周期状态、时间和结果摘要。无权限时服务端下发空快照以清除客户端旧状态，读取失败则下发结构化错误。客户端断线时同样清空这些镜像。

## 命令接口

命令是当前核心功能的主要入口，也可视为未来 UI 应调用的用例边界。主要工作流包括：

```text
/parcel <selector> save [ignore_entities]
/parcel <selector> commit [message]
/parcel <selector> history [limit]
/parcel <selector> restore <revision> [ignore_entities]

/parcel <selector> publish <repository> <path> [message]
/parcel <selector> bind <repository> <path>
/parcel <selector> unbind
/parcels import <repository> <path> <position> [mirror] [rotation]

/parcels repositories list
/parcels repositories create <name>
/parcels repositories clone <name> <https-url>
/parcels repositories fetch|pull|push <name>
/parcels operations [id]
```

命令层负责解析输入、检查权限、形成用户可读反馈，并调用服务层。格式编解码、路径解析、Git 操作和世界写入不应堆积在命令实现中，以便未来 Modern UI 复用相同能力。

## 安全设计

### 路径安全

所有来自命令、配置、共享元数据和 Git 树的路径都视为不可信输入。路径解析后必须仍位于预期根目录内，并拒绝：

- 绝对路径。
- `..` 等目录逃逸。
- 空路径或无效名称。
- `.git` 内部路径。
- 与保留文件 `meta.json` 的冲突。
- Git 历史中的符号链接和特殊文件。

校验应发生在真正访问文件系统之前，不能仅依赖命令参数类型或字符串前缀。

### 远程地址与凭据

受管远程仓库只接受不含凭据的 HTTPS URL，拒绝 HTTP、SSH、文件协议，以及包含用户名、密码、查询参数或片段的地址。

当前远程凭据从进程环境变量 `GITPARCEL_GIT_USERNAME` 和 `GITPARCEL_GIT_TOKEN` 读取。凭据不得写入仓库配置、地块数据、操作详情或日志。系统存储提供的 secrets 目录是未来可扩展位置，但不是当前 Git 凭据工作流的一部分。

### 破坏性操作

共享仓库当前不提供删除命令。以后加入删除、强制覆盖、历史重写等能力时，必须单独设计引用检查、二次确认、可恢复策略和审计信息，不能复用普通配置权限后直接删除。

## 一致性与失败语义

系统优先选择显式失败而不是静默修复：

- 快照生成失败时保留原地块目录。
- 新快照安装失败时尝试恢复备份。
- Git 无变化时返回“未提交”，而不是制造空版本。
- 仓库非干净状态、历史分叉或远程配置不完整时拒绝同步。
- 共享元数据与地块内容不匹配时拒绝绑定或导入。
- 历史版本的几何信息不兼容时拒绝写入世界。
- 远程任务失败只改变任务状态，不在后台隐式重试或修改世界。

文件系统替换和 Git 提交能覆盖大部分本地原子性需求，但它们不能与 Minecraft SavedData 形成真正的跨系统事务。因此用例顺序应保证每一步都可重试，并尽量让失败留下可诊断、不会误覆盖已有数据的状态。

## 多加载器与版本兼容

Fabric 和 NeoForge 只负责注册入口、生命周期事件、网络接入及版本特有 API。领域模型、存储格式、Git 规则和大部分 Minecraft 逻辑保持共享。

Minecraft 权限 API、注册方式、网络接口和数据组件在不同版本间可能变化，这些差异应集中在版本或平台适配层，不能扩散到领域模型。持久化数据使用 Codec 和显式格式版本，旧的直接仓库位置仍可解码，以便逐步迁移到共享仓库符号位置。

新增持久化字段时应满足以下原则：

- 有合理默认值，旧存档可以读取。
- 能通过当前 Codec 明确表达缺失与非法状态。
- 改变内容解释方式时提升相应格式版本。
- 需要迁移 Minecraft 数据时保留原 `dataVersion`。

## Modern UI 演进边界

未来 Modern UI 应建立在已有服务端用例之上，建议首先覆盖：

- 地块列表、详情、选择与权限可见性。
- 保存、提交、历史查看与恢复确认。
- 共享仓库列表、发布、绑定和导入。
- 异步 Git 任务的排队、进度、结果和错误展示。
- 服务端格式能力和格式配置编辑。

当前已经具备共享仓库摘要和操作详情的结构化查询协议。UI 设计前还需要补足分页历史等面向界面的查询。协议应返回结构化数据，而不是复用命令输出文本。命令和 UI 应共同调用服务层，而不是互相调用。

现有调试界面可以继续用于开发验证，但不要求与最终 Modern UI 保持结构或视觉兼容。

## 测试策略

测试按风险分层：

- 领域单元测试：路径、位置 Codec、权限复制、格式规格和纯算法。
- 文件系统测试：完整快照替换、失败回滚、共享目录与元数据原子更新。
- Git 集成测试：无变化提交、按路径历史、非 checkout 恢复、共享元数据原子提交、快进约束和仓库锁。
- Minecraft GameTest：创建、保存、加载、恢复及世界状态同步等核心用例。
- 架构检查：限制客户端、公共逻辑、平台适配和服务端实现之间的依赖方向。
- 多加载器构建：至少验证所有目标 Fabric/NeoForge 版本能够编译和打包。

涉及数据丢失、路径逃逸、权限绕过和并发写入的修复必须附带回归测试。单纯通过编译不足以证明存储或 Git 工作流安全。

## 当前限制与后续方向

当前核心链路已经覆盖本地地块保存、提交、历史、恢复，以及共享仓库的发布、绑定、导入和异步远程同步。下一阶段宜继续完善核心能力，而不是先重构界面：

- 为地块 Git 历史提供可鉴权、可分页的结构化网络查询。
- 完善跨文件系统失败注入测试和 Git 并发测试。
- 设计远程认证的安全配置方式，减少对进程环境变量的依赖。
- 明确共享地块更新到实时世界的用户确认与预览流程。
- 为旧持久化位置和格式升级建立可测试的迁移策略。
- 在引入共享仓库删除、强制同步或冲突解决前，先完成独立的安全设计。

只有当服务层接口在命令与网络场景中稳定后，才开始最终 Modern UI 的交互和视觉设计。这样可以避免界面反过来固化尚未成熟的业务模型。
