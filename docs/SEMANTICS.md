# 记录语境语义规约

本文形式化 parcel 捕获与恢复中"语境依赖数据"的处理语义。parcel 的记录可以是实体、方块实体或扩展注册的其他记录。文中定义、不变式与性质是 [DESIGN.md](DESIGN.md) 全部设计的语义基础。除第 9 节的缺口登记与第 11 节的机制映射记录实现与规约的对账状态外，本文代表目标而非当前实现的清单；实现与本文冲突时，后续开发应向本文收敛。

## 1. 语境

**定义 1.1（世界语境）** 世界语境是捕获与恢复之间可能变化的四类环境：

| 分量 | 内容                                  | 恢复时的变化                      |
| ---- | ------------------------------------- | --------------------------------- |
| 空间 | 正交变换 `(R, t)`（旋转、镜像与平移） | parcel 可恢复到不同锚点或不同朝向 |
| 身份 | 世界分配的离散句柄（实体 UUID 等）    | 恢复批次重新分配                  |
| 资源 | 存档层外部存储（地图数据等）          | 句柄在新存档中重新分配            |
| 时间 | 游戏刻 `gameTime`                     | 单调推进，绝对时刻失去意义        |

**公理 1（语境依赖性）** 世界序列化数据面向原地读回设计，不保证脱离原语境后仍语义正确。

**公理 2（语义不可推断性）** 仅凭 NBT 结构无法可靠推断字段的语境语义：同一路径在不同类型上语义不同；字符串等不透明载荷内嵌的语境信息不可靠地检测，任何尝试都会误改玩家数据。

**推论 1（注册制）** 语境语义知识必须由语义拥有方以处理器显式注册：原版字段的处理器由本模组内置，模组字段的处理器由该模组经 `GitParcelExtension` 注册。处理器必须绑定类型过滤器，以处理“同一路径、不同类型、不同语义”。

**推论 2（能力边界）** 对不透明载荷中的语境信息，本规约不检测、不变换、不宣称。

**推论 3（变化语义不可推断）** 无法从两次捕获的值差异推断该变化是否携带语义：语义性取决于记录之间的结构关系，而这种关系往往不存在于数据模型中——羊穿过栅栏只体现为两个坐标之间的少量位移，"被围住"这一关系本身无处可读。因此瞬态与派生的判定只能由语义拥有方以处理器逻辑或记录级配置显式给出，不能基于位移幅度等值级启发式。位置与朝向字段没有中间道路：要么原样记录，要么随整个记录流不保存。

## 2. 记录模型

**定义 2.1（记录）** 记录由三部分构成：

- 定位字段 `position(r)`：序列化协议为记录约定的自身空间位置；
- 载荷 `payload(r)`：自包含数据，捕获与恢复之间无需变换；
- 边集 `E(r)`：指向记录自身之外的一切引用。

**定义 2.2（定位字段）** 每条记录有一个权威定位：实体记录的 `pos` 与 `blockPos` 元组，方块实体在 section 中的存储位置。NBT 内的方块实体根 `x/y/z` 与实体的 `Pos`、`block_pos` 是权威定位的派生副本，由管线无条件按权威定位重写，从不携带独立语义；但它们随权威定位同步变化，其 diff 是权威变化的组成部分，不属于消除范畴，不做特殊对待。定位字段是记录级概念；parcel 的锚点（定义 1.1）是空间层的坐标系原点，二者含义不同。实体的 `Rotation` 与 `Motion` 则携带捕获瞬间的独立信息，语义性随记录类型变化：`Rotation` 对作为作品的记录是语义（盔甲架是雕塑，朝向即作品本身），对自主移动的生物是候选噪声；`Motion` 是预测性状态（恢复后是否继续该运动），对投射物是语义（飞行中的箭恢复后应继续飞行），对生物是候选噪声。二者不存在无条件消除，只能由按记录类型编写的处理器处置（定义 2.5、规则 2.2）。`Passengers` 是包含结构而非引用边：子记录随父记录整体搬运，其定位字段逐层独立变换，处理器按每层乘客自身的类型过滤。

**定义 2.3（引用边）** 按指向目标的性质分四类：

| 边     | 指向                                 | 实例                                                                     | 承载机制                    |
| ------ | ------------------------------------ | ------------------------------------------------------------------------ | --------------------------- |
| 空间边 | 世界空间中的位置或方向               | 蜂巢 `flower_pos`、Mob `home_pos`、`leash` 坐标形态、折跃门 `ExitPortal` | 处理器经 `ParcelSpace` 换算 |
| 身份边 | 批次内的其他记录，或批次外的存活对象 | `leash.UUID`、驯服主人                                                   | 处理器 + 批次句柄翻译       |
| 资源边 | 存档层外部存储                       | 地图 `map_id`                                                            | 附件                        |
| 时间边 | 与 `gameTime` 绑定的时刻             | 计划刻的触发时间、冷却截止时刻                                           | 时间相对化                  |

**定义 2.4（边界类别）** 不属于记录但属于 parcel 语义的数据有两类：区域贡献（不被任何记录引用的区域性世界状态，经贡献者在边界时机搬运）和不透明载荷（推论 2 的适用对象）。

**规则 2.1（形态分派）** 同一路径可能有多重形态（`leash` 可以是 UUID 形态或坐标形态）。每种形态归入恰好一类边，由对应机制处理；任何一条数据不得被两类机制同时改写。

**定义 2.5（瞬态与派生载荷）** 载荷中变更不携带语义的易变字段（受击红闪、速度、模组日志时间戳），以及由全局环境派生的字段（计划刻触发时刻、冷却截止时刻），统称瞬态与派生载荷。

**规则 2.2（消除判据）** 易变字段进入消除范畴的判据是其变更不携带语义信息，而不是恢复时可重算。消除只适用于携带独立信息的字段：派生定位副本（定义 2.2）不携带独立信息，不在消除范畴内，随权威定位同步重写，其 diff 随权威变化正常呈现。可重算的有语义字段必须原样记录：栅栏与玻璃板的连接形状、红石功率等由邻居方块派生的状态，其变更或由 parcel 内邻居的变化引起（diff 因果可见），或忠实反映 parcel 与外界的边界交互；若在捕获时剥离，恢复结果将依赖快照之外的世界状态，破坏迁移正确性。消除经声明通道（`ELIMINATE`）在捕获时移除字段，快照与恢复记录中字段缺席即引擎默认值，恢复侧不做删除动作；消除类处理必须在核心处理器的定位重写之后执行（不变式 6.1）。

**规则 2.3（相对化）** 时间相对化把对全局时间轴的绝对引用改写为快照内偏移：捕获时存 `value − gameTime`，恢复时写回 `gameTime' + 偏移`。它与空间相对坐标、句柄翻译表是同一动作的三个实例——把快照之外的依赖搬进快照之内。相对时长字段（熔炉剩余进度、蜂箱 `TicksInHive`）本身自包含，原样保留。

## 3. 空间变换

**定义 3.1（parcel 变换）** parcel 的放置变换是正交变换 `T = (R, t)`：`R` 为含反射的旋转与镜像（正交矩阵），`t` 为平移。原位恢复时 `T` 为恒等。锚点是归档局部坐标系的原点与子区格点的对齐基准，其世界绝对坐标由 parcel 记录（见 DESIGN.md 的“锚点参照系与子区对齐”）。

**规则 3.1（值语义）** 点变换为 `R·p + t`；向量变换为 `R·v`，不受平移；朝向只受旋转与镜像。处理器为每个字段认定语义角色（点、向量、朝向），并经 `ParcelSpace` 按角色施加变换。朝向角色的处理必须覆盖其值域形态：除 yaw/pitch 外还包括标量步进角度（如物品展示框的 `ItemRotation`）与方向枚举（`Direction` 的字符串或整数编码）。声明字段通道为此提供两种朝向编码：`DIRECTION`（字符串名或 3D 数据值整数，按朝向角色换算，写回保留原形态）与 `ROTATION_STEP`（45° 面内步进角）。步进角的语义以向量方式定义，由 `ParcelSpace` 单点换算：步进 r 的物品顶向量是参考顶向量绕框架朝向轴旋转 −45°×r 的结果（墙面框架的参考顶为世界上方，地面/天花框架的参考顶按原版渲染约定取固定水平方向）；变换时顶向量按向量角色变换、朝向按朝向角色变换，步进取参考顶到变换后顶向量的 45° 量化角。由此墙面框架在旋转下步进不变、镜像下取反；地面/天花框架在旋转下每顺时针 90° 步进 +2，镜像效果随顶向量与镜像轴的相对关系而异。同记录内声明为 `DIRECTION` 的字段为步进换算提供框架朝向（取换算前的原值），缺失时按墙面框架惯例（镜像取反、旋转不变）处理。

**定义 3.2（内指与外指）** 空间边按捕获时目标位置是否落在 parcel 范围内分为内指与外指。判定以几何检测为默认，处理器可显式覆盖。

**规则 3.2（空间边变换）** 捕获时对内指边施加 `T⁻¹`，恢复时施加 `T`；外指边在两侧均保持恒等。声明的空间坐标字段（`BLOCK_POS`、`BLOCK_POS_XYZ`、`POSITION` 编码）在两侧各做一次几何检测：捕获时把目标世界坐标逆变换到 parcel 空间，落在内容范围 `[-anchor, size - anchor)`（半开区间）内即内指、否则外指；恢复时对存储值做同一范围检测，内指施加 `T`、外指保持原值。两侧检测相互印证——内指边存储 parcel 相对值（落在范围内），外指边存储世界原值。检测的固有歧义（靠近坐标原点的 parcel，其相对范围与世界坐标重叠）按已知局限接受，需要精确语义的领域以覆盖声明消解：字段可声明 `GEOMETRIC`（默认，如上检测）、`INSIDE`（恒按内指变换）或 `OUTSIDE`（恒恒等）。无几何信息（上下文未携带 parcel 范围）时退化为恒按内指变换。

**不变式 3.1** 迁移放置后，每条内指边在新坐标系下仍指向同一逻辑目标；每条外指边保持捕获时的世界值。

外指边取恒等的理由：外指目标不随 parcel 迁移，若施加 `T`，变换后的坐标指向一个从未存在过目标的位置，比保留对旧世界的陈旧记忆更差。整体清除是将来可选的策略，不是默认。

**规则 3.3（变换单一定义点）** 镜像与旋转的复合顺序、复合时镜像轴的对换规则，由 `ParcelSpace` 唯一定义。处理器不得自行组合变换，只能请求 `ParcelSpace` 施加完整变换。

**规则 3.4（方块状态变换）** 方块状态经原版 `BlockState#rotate` 与 `BlockState#mirror` 变换：捕获时施加逆变换存入归档（规范朝向），恢复时施加正变换放回世界；复合顺序与规则 3.3 同源，由 `ParcelSpace` 唯一定义。每个方块自身的属性语义只有它自己知道，外部属性映射表不可替代这一机制。未覆写 `rotate`/`mirror` 的模组方块静默保持捕获时朝向，保真度按规则 7.1 评定。

## 4. 句柄翻译

**定义 4.1（句柄与翻译表）** 句柄是世界分配的离散身份。翻译表 `M` 把旧句柄映射到新句柄。

**规则 4.1（两阶段）** 记录级：进入批次缓冲前，从记录中抽取全部旧句柄，与记录一并缓冲，此后记录内的根句柄字段视同失效；批次级：在 `commit` 时机一次性分配 `M`，写回根句柄，处理器据此重写全部身份边（含 `Passengers` 子树），然后才允许生成记录。

**不变式 4.1（表完备）** `M` 的键集等于批次内全部旧句柄。分配与生成不得发生在批次中途：半批生成意味着某些记录引用的句柄已被分配，而它们指向的记录不存在。

**不变式 4.2（表外恒等）** `M` 中不存在的引用保持原值。批次外目标（玩家、其他 parcel 中的实体）不受本次恢复影响，原值恰好继续指向它们。

实体 UUID 的翻译由 `EntityUuidRemapper` 实现；地图编号的翻译经附件回填实现（第 5 节）。二者是同一模式的两例。

## 5. 资源边与附件

**规则 5.1** 资源边按"物化 + 翻译 + 原句柄保留"处理：捕获时把句柄背后的内容提取为附件，附件按内容寻址，相同内容自然去重；恢复时把附件重新物化到目标世界，取得新句柄，经翻译重写记录中的引用；同时 NBT 中保留原句柄。

**规则 5.2（失败语义）** 附件类型未注册，或 schema 版本不精确匹配时，显式失败。

**规则 5.3（降级适用）** 原句柄保留使"类型缺失"场景的行为退化为引用旧句柄，可预期、不崩溃；这是降级而非正确恢复，保真度评定见第 7 节。

## 6. 处理管线

恢复侧按以下顺序执行，捕获侧为同一管线的逆向：

1. 数据版本迁移；
2. 记录级处理器链（按 `runAfter`/`runBefore` 全序化）：核心归一化处理定位字段，其余处理器随后处理空间边与载荷；
3. 批次级句柄翻译（规则 4.1）：分配 `M`，处理器重写身份边；
4. 附件回填，重写资源边句柄；
5. 贡献者恢复钩子，此时可访问全部附件记录与已应用的世界状态。

**不变式 6.1（次序确定性）** 处理器全序由各处理器注册的 `runAfter`/`runBefore` 唯一确定，同一输入产生同一处理序列。记录级管线先于批次级翻译执行，这正是规则 4.1 要求在记录级抽取旧句柄的原因：记录级处理器可能改写或删除根句柄字段。消除类处理必须在核心处理器的定位重写之后执行，否则其移除的字段会被重写恢复，消除静默失效。

**规则 6.2（实体替换语义）** 恢复采用替换语义：先按捕获谓词清除 parcel 区域内已有的非玩家实体，再放置方块，最后批次生成快照实体。清除谓词必须与捕获谓词是同一函数（AABB 相交、非玩家、非乘客的根实体判定，乘客树随根）；玩家永不清除。

**不变式 6.2（替换完备）** 恢复完成后，parcel 区域内可见的实体集合与快照实体集经放置变换后的像同构：既无残留（旧实体已清除），也无缺失（除非显式配置忽略实体）。`ignoreEntities` 配置下清除与放置同门，均不发生。

**规则 6.3（计划刻替换语义）** 区域内不隶属任何记录的方块计划刻与流体计划刻按替换语义搬运：恢复时先清除 parcel 区域内已有的全部计划刻（方块与流体同门，`ignoreBlocks` 配置下清除与重灌均不发生），再重灌快照记录的计划刻。计划刻的定位即其目标方块位置，永远内指（落在内容范围内）；捕获时随空间边经 `T⁻¹` 变换为锚点相对坐标，恢复时施加 `T`。触发时刻按规则 2.3 相对化：捕获时存 `triggerTick − gameTime`，恢复时写回 `gameTime' + 偏移`；偏移可为负（目标时刻已过），恢复后的首次计划刻调度即触发，与原版区块加载对未到时计划刻的容忍一致。重灌前对同位同类型的既有刻先删后插——快照是权威，恢复放置方块引发的自动计划刻不得遮蔽快照刻。无法解析的刻类型（方块或流体注册表中不存在）构成失败（规则 7.1），不做静默跳过。

**不变式 6.3（计划刻替换完备）** 恢复完成后，parcel 区域内的计划刻集合与快照计划刻集经放置变换后的像按（位置、类型）逐一等价：既无残留（区域内旧刻已清除），也无缺失（除非显式配置忽略方块）。区域外的计划刻不受恢复影响。

## 7. 保真度

**定义 7.1（保真度四级）** 任一数据在一次操作中的结果分为：精确、透传、降级、失败。

**规则 7.1（等级评定）** 等级是处理器覆盖状态与操作场景的函数，不是字段的固有属性：

- 已被处理器覆盖：精确；
- 未被覆盖：原位恢复下等同于精确（恒等变换），迁移下为透传（未知的位置敏感字段可能指错）；
- 方块状态属于未覆写 `rotate`/`mirror` 的模组方块：原位恢复下等同于精确，迁移下为透传（保持捕获时朝向，规则 3.4）；
- 资源边缺少可解析附件：降级（规则 5.3）；
- 宣称支持的数据缺失或损坏：失败。

**规则 7.2（快照自述）** 快照记录捕获时生效的处理器与附件类型清单。恢复前对比清单，因缺失而将降级的部分必须显式告知，不得静默。

**规则 7.3（按自述解释）** 恢复时处理器的参与以快照自述清单为准，而非当前注册表：快照未记录的处理器一律不参与变换，即使当前已注册。这消除了“捕获时未覆盖、恢复前补覆盖”的错位——否则保存在 NBT 中的世界绝对坐标会被当作 parcel 相对坐标错误换算，指向错误位置且不报错。声明字段（坐标字段与实体引用字段）作为声明处理器的数据，同样逐条按清单裁决：清单未记录的字段不参与重写。核心定位处理器承载权威定位的无条件重写（定义 2.2），不适用本条，始终参与。清单整体缺失的快照按最保守方式解释：仅核心处理器参与，其余处理器与字段重写一律不发生，其结果按规则 7.1 评定。

**规则 7.4（扩展标识与覆盖）** 每个扩展条目（处理器、附件类型、内容类型）拥有稳定的完全限定 ID（`namespace:path`）。ID 一经快照自述引用即不可变更；改名视为删除并新增，旧 ID 按规则 7.3 处理。同一 ID 重复注册不得失败。属主地位由扩展显式声明的属主命名空间集合判定（默认为其 ID 的命名空间；本模组内置扩展声明 gitparcel 与 minecraft）：属主永远优先于客人，与加载顺序无关；同为客人或同为属主时，显式注册优先级高者生效，同优先级时扩展 ID 字典序较小者生效。被覆盖的注册不生效，也不进入快照自述；裁决结果记入日志。

## 8. 性质

以下性质是验收标准，每条都应可转化为测试：

- **P1（往返不变性）** 捕获后立即原位恢复，结果语义等价：载荷中语义字段逐值相等（瞬态与派生字段按其处理器策略等效），定位像相等，空间边逐值相等，身份边图同构（句柄值可变，边一一对应），实体集合满足不变式 6.2。
- **P2（迁移正确性）** 对任意 `T`：内指空间边满足不变式 3.1，身份边满足不变式 4.2，恢复结果不依赖 parcel 之外的世界状态。
- **P3（规范形确定性）** 相同的 parcel 内容与配置产生逐字节相同的快照文件树。噪声源限于四类，各有对应机制：易变瞬态字段（消除处理）、绝对时间戳（相对化）、实体枚举顺序（稳定排序）与浮点抖动（归一化）。
- **P4（覆盖完备性）** 对目标序列化面的审计清单（第 9 节）与已注册处理器的覆盖一致。
- **P5（替换幂等）** 对同一 parcel 连续两次恢复同一快照，第二次恢复后区域内的实体集合与第一次相同：不因恢复而实体翻倍。

P1、P2、P5 进入 GameTest 基座并对扩展注册的处理器自动生效；P3 进入格式测试；P4 进入审计流程。

## 9. 审计与缺口登记

审计方法：对目标版本每个方块实体与实体的序列化方法（保存侧与加载侧）做静态清单，把其中每个语境依赖字段按四类边归档，与已注册处理器的覆盖对账；版本升级时重跑。

已确认缺口（实现应向本节收敛）：

- 时间边：计划刻（方块刻与流体刻）经 `scheduled_ticks` 内容类型搬运（规则 6.3）：内指计划刻随 parcel 变换坐标，触发时刻按规则 2.3 相对化，恢复时清除后重灌。方块实体内的时间边字段已按审计补齐相对化声明（Vault `state_updating_resumes_at`、TrialSpawner `next_mob_spawns_at` 与 `cooldown_ends_at`、Interaction `attack`/`interaction.timestamp`）。
- 空间边：声明字段通道已按审计补齐原版位置字段（`home_pos`、蜜蜂 `hive_pos`/`flower_pos`、`sleeping_pos`、`anchor_pos`、`patrol_target`、`bound_pos`、`wander_target`、`beam_target`、末地折跃门 `exit_portal`）；`TileX/Y/Z` 在 26.x 已演进为 `block_pos` 并由核心处理器无条件重写。Brain 记忆中的位置类记忆（GlobalPos 复合、跨维度）登记为不处理，村民迁移评为透传。
- 瞬态与派生处理：消除与偏移相对化已实现；按持有者 tickCount 折算的相对计数、Brain 记忆 `ttl`、物品冷却与熔炉键名核对、以及浮点归一化仍未处理。
- 实体替换：恢复已按 AABB 相交、非玩家的谓词清除区域内旧实体，不变式 6.2 与 P5 成立；清除尚未按捕获谓词的根实体判定执行——乘客被逐个清除而非随根整树搬运，跨界载具的边界乘客存在重复或悬空的边角情形。

## 10. 已知局限

- **反向边不可见**：parcel 外对象指向 parcel 内记录的边不随恢复更新。原版数据大多把引用存在从属一方（拴绳边在被拴者身上），因此此类案例稀少；模组可能不遵循该惯例，扩展作者应知晓此局限。替换语义（规则 6.2）下，parcel 外对象指向被替换实体的边（如玩家拴向 parcel 内动物的拴绳）会在恢复后悬空，这是替换的必然代价。
- **实体模型不镜像**：镜像放置只变换实体的位置与朝向，实体模型的手性（不对称的外观细节）不翻转；Minecraft 不提供镜像实体渲染的能力，几何上的完美镜像对实体外观不可达。
- **不透明载荷**：见推论 2。
- **方块状态透传**：未覆写 `rotate`/`mirror` 的模组方块在迁移恢复下保持捕获时朝向（规则 3.4、规则 7.1 评为透传）。这是接受的已知行为，不做恢复前告知；其判定依赖对模组类的反射式检查且可操作性弱，规则 7.2 的告知义务不涵盖此类固有行为。
- **非原子捕获**：捕获表示一段时间内观察到的内容，见 DESIGN.md"大规模 Parcel 与操作进度"。
